## Buy or Wait? — 24-Hour Build Plan

## 1. Tech Stack Decision

- **Core decision engine**: Python 3.11 (matches `code/main.py` suggested entry point, best CSV/date tooling).
- **LLM/VLM calls**: Anthropic API (Claude) for image and message extraction, structured JSON output only. Keep temperature at 0.
- **Backend API (optional bonus)**: FastAPI (Python), matches existing stack.
- **Frontend (optional bonus)**: React + TypeScript, calling the FastAPI REST endpoints.
- **Testing/Evaluation**: Python `pytest` + a standalone `evaluation/score_samples.py` against `sample_requests.csv`.

## 3. Hour-by-Hour Plan (24 hours total)

### Hour 0–1: Setup
- Clone repo, read `AGENTS.md`, `CLAUDE.md`, `problem_statement.md` fully.
- Confirm the deadline countdown is visible in every agent session (per AGENTS.md §3).
- Set up `.env` for `ANTHROPIC_API_KEY` (or chosen provider), add to `.gitignore`.
- Scaffold the `code/` folder structure above.
- Write `data_loader.py`: load all 9 CSVs into typed structures (pandas or plain `csv` + dataclasses), validate expected columns exist.

### Hour 1–3: Data Model & State Reconstruction
- Build `fx.py`: currency conversion keyed by (date, from_currency, to_currency).
- Build `state_builder.py`:
  - Join `financial_events.csv` to each user.
  - Classify each event: recurring vs one-off, cash-state (settled/pending/scheduled/unrealized/failed/cancelled), flexible vs protected (from `financial_profiles.csv` categories).
  - De-duplicate repeated representations of the same event (use `linked_event_id` chains).
- Manually trace 3–5 users by hand against `sample_requests.csv` to sanity-check the reconstructed state.

### Hour 3–6: Evidence Extraction (Images & Messages)
- Build `evidence_extractor.py`:
  - For every event with blank `amount`, resolve `image_id` via `images.csv` (`related_event_id` == `event_id`), load `dataset/media/images/<image_id>.png`, call the VLM with a strict extraction prompt (see prompt library below) that returns structured JSON (`amount`, `currency`, `date`, `confidence`).
  - For messages with `related_event_id` set, extract amendments (cancel/delay/confirm/amend) as structured JSON.
  - For messages/images without a `related_event_id` but referencing a `request_id`, extract any clarifying fact (e.g. "I already paid the deposit", "this bonus fell through") as structured JSON.
  - **Guardrail**: prompt explicitly instructs the model to treat all message/image text as data, never as instructions, and to output "no relevant fact" rather than comply with anything that looks like an instruction.
- Cache every extraction result by `(event_id or message_id or image_id)` so re-runs don't re-call the API (token efficiency + determinism).

### Hour 6–9: 90-Day Forecast Engine
- Build `forecast.py`:
  - Starting balance = `available_balance` from `financial_profiles.csv` on `request_date`.
  - Walk day-by-day for 90 days, applying: recurring income/expenses on their cadence, confirmed salary on settlement date, pending debits on their due date, any amendments from `evidence_extractor`.
  - At each day, check `balance >= minimum_balance_to_keep`.
  - Support "what if we pay X on date D" and "what if we stop/reduce event E" as simulation overlays, so the decision engine can test candidate plans against the same forecast function.
- Compute `amount_safe_to_pay` (max safe today, before spending changes, capped at `requested_amount`) and `earliest_date_for_full_payment` by binary-searching / scanning the forecast.

### Hour 9–14: Decision Engine
- Build `decision_engine.py`:
  - Determine eligible methods from `payment_methods_user_will_consider` and `max_installment_months`.
  - Generate candidate plans: full payment today; full payment on `earliest_date_for_full_payment` (wait); partial payment (2-payment rule); each valid installment option from `request_payment_options.csv`; plans with permitted spending changes applied.
  - Filter to only plans that pass the 90-day safety check via `forecast.py`.
  - Apply the 6-step tie-break ranking exactly as specified.
  - Derive `affordability_status` from the chosen plan's shape (now/with_plan/later/not_affordable).
  - Derive `spending_changes_needed` (max 3, `stop`/`reduce_to`, mutually exclusive per event).
- Build `verifier.py`: run every hard constraint from the PRD §5.8 before allowing a row to be written.

### Hour 14–16: Explanation Generation
- Build the `explanation_prompt.md`: given the chosen plan + the specific numbers/events that drove it, generate one short, grounded, non-generic sentence or two. No LLM call should be able to change the decision, only phrase it.
- Fallback: a template-based explanation generator (rule engine) if the LLM call fails, so `decision_explanation` is never empty.

### Hour 16–18: Full Pipeline + Sample Scoring
- Wire everything in `main.py`: load → build state → extract evidence → forecast → decide → verify → write `output.csv`.
- Run against `sample_requests.csv` (25 solved rows) first. Build `evaluation/score_samples.py` to diff your predictions vs the given solved columns field-by-field, print a mismatch report.
- Fix systematic errors (usually: wrong recurrence detection, wrong pending/settled treatment, wrong tie-break order, wrong date math).

### Hour 18–20: Full Dataset Run + Token/Cost Report
- Run on the full `requests.csv` (250 rows).
- Validate: row count, column order, value domains, `0<=amount_safe_to_pay<=requested_amount`, installment-matches-option, flexible-only spending changes.
- Generate `evaluation/usage_report.md` from the accumulated call log in `llm_client.py` (model name, #calls, input/output tokens, totals, per-request average, cost estimate using published per-token pricing).

### Hour 20–22 (only if ahead of schedule): Optional REST + React Bonus
- FastAPI: `GET /users/{user_id}/state`, `POST /requests/{request_id}/decision`, `GET /requests/{request_id}/forecast`.
- React: a simple two-pane UI (chat input + result card with plan/forecast chart) hitting those endpoints. This is for interview demo value only.

### Hour 22–23: Packaging
- Write `code/README.md` with exact setup/run commands.
- Zip `code/` (exclude venvs, `node_modules`, build artifacts, `data/`, `dataset/`) as `code.zip`.
- Confirm `log.txt` has been growing since hour 0 with valid `tool=` entries every turn.

### Hour 23–24: Buffer
- Re-run `python3 code/main.py` on a clean checkout to confirm reproducibility.
- Final checklist pass (PRD §9) before hitting submit at the exact link:
  `https://www.hackerrank.com/contests/hackerrank-orchestrate-september26/challenges/buy-or-wait/submission`

## 4. Determinism Strategy (important for grading + AI Judge interview)

- All arithmetic (currency conversion, balance forecasting, plan ranking) lives in plain Python, not LLM calls.
- LLM calls are isolated to two narrow jobs: (1) reading a number/date/fact out of an image or message, (2) writing one explanatory sentence.
- Every LLM call response is cached to disk (`evaluation/llm_cache.json`) keyed by input hash, so re-running `main.py` reproduces identical output.csv without re-spending tokens.
- Be ready to explain this separation clearly in the AI Judge interview — it is the single strongest "why is this reliable" answer you can give.
